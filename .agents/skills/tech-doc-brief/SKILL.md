# 개발자용 기술 문서

특정 기술을 도입할지 판단하고 실제로 적용하는 데 도움이 되는 한국어 문서를 작성한다. 기본 산출물은 채팅 안의 복사 가능한 Markdown이다. 사용자가 다른 언어·분량·출력 형식을 지정하면 그 요청을 따른다.

## 요청 해석

- 기술명과 대화의 작업 맥락을 활용한다. 예를 들어 Unreal의 PCG 재료에 관한 대화라면 해당 기술을 PCG에서 어떻게 활용할지도 다룬다.
- 기술을 식별할 수 있으면 바로 조사하고 작성한다. 약어가 여러 기술을 가리키거나 버전에 따라 핵심 결론이 달라질 때만 필요한 정보를 질문한다.
- 간단한 정의 질문에 전체 양식을 강제하지 않는다. 기술 정리·개발 문서·노션용 문서 요청일 때 이 형식을 사용한다.
- 문서 작성 요청만으로 Notion 페이지를 생성하거나 수정하지 않는다. 실제 게시가 요청되면 연결된 도구와 해당 작업의 지침을 따른다.

## 근거 확인

- 버전별 동작, 지원 범위, API, 사용 절차, 성능 관련 주장은 공식 문서·API 레퍼런스·공개 소스·공식 이슈 등 1차 자료로 확인한다. 확인할 수 없으면 그 범위를 짧게 밝힌다.
- 사용자가 버전을 주면 그 버전을 우선한다. 버전을 주지 않았고 차이가 중요하면 확인한 문서 버전을 표시한다. 최신 문서가 사용자의 설치 버전과 같다고 가정하지 않는다.
- 공식 사실, 설명을 위한 예시, 작성자의 설계 제안을 구분한다. 권장 구성은 '설계 제안'임을 명시하고 공식 필수 구조처럼 쓰지 않는다.
- 측정 자료가 없으면 FPS 상승률, 메모리 감소율, 드로 콜 수를 만들어 내지 않는다. 비용을 줄이는 원리와 효과가 달라지는 조건을 설명한다.
- 근거 링크는 해당 주장을 뒷받침하는 문장이나 문단 가까이에 붙인다. 검색 결과의 요약문만으로 중요한 결론을 확정하지 않는다.

## 문서 구성

한 줄 정의와 사용 목적을 먼저 제시하고, 다음 항목 중 해당 기술에 유용한 내용을 선택한다. 기본적으로 아래 흐름을 유지하되 불필요한 항목은 생략하고 분량을 고정하지 않는다.

1. **기술명과 개념**: 무엇을 입력받아 어떤 결과를 만드는지, 개발자가 이해해야 할 내부 동작을 짧게 설명한다.
2. **사용했을 때의 장점**: '장점 / 개발 시 얻는 효과' 표로 정리한다. 추상적인 '최적화' 대신 어느 비용이나 작업이 줄어드는지 적는다.
3. **사용하기 좋은 상황**: 구체적인 대상·문제와 예시를 표로 제시한다. 적합하지 않은 상황도 함께 판단할 수 있게 한다.
4. **지원 범위와 제약**: 지원되지 않는 구성, 보존되지 않는 기능, 개별 제어·런타임·스트리밍 등 실제 적용에 영향을 주는 제한을 다룬다. 관련 없는 위험을 나열하지 않는다.
5. **유사 기술과 선택 기준**: 혼동하기 쉬운 대안이 있을 때만 '상황 / 우선 검토할 기술'로 비교한다. 목적이나 구현 수준이 다른 기술을 단순 우열로 비교하지 않는다.
6. **현재 작업에서의 적용 예시**: 대화 맥락에 맞춘 구성 예시를 제공한다. 구조가 도움이 되면 짧은 텍스트 트리나 코드 예시를 사용한다. 확인하지 않은 예제를 실행 검증했다고 표현하지 않는다.
7. **실무 확인 사항**: 도입 결과를 확인할 구체적인 항목을 추린다. 성능 기술이면 동일 조건의 전후 측정, 제작 워크플로면 수정 반영과 결과물 검증을 포함한다.
8. **문서에 사용할 핵심 문장**: 기술의 목적·적합한 상황·핵심 제약을 담은 2~3문장의 인용 블록으로 마무리한다. 이미 짧은 문서라면 생략한다.

## 문체와 품질

- 문서 본문은 자연스럽고 간결한 한국어 설명체로 쓴다. 불필요한 서문 없이 완성된 문서를 제공한다.
- 제품명·API·노드명은 검색 가능한 원문을 유지하고 약어는 처음에 풀어 쓴다.
- 비교와 매핑에는 표를, 독립적인 제약과 검증 항목에는 짧은 목록을 사용한다. 서식은 붙여 넣기 쉬운 Markdown으로 유지하며 상위 지침의 서식 제한을 따른다.
- 사용법 전체 튜토리얼이나 기능 목록으로 확대하지 않는다. 독자가 '왜 쓰는지, 언제 쓰는지, 무엇을 잃거나 확인해야 하는지' 판단할 수 있는 정보를 우선한다.
- 전달 전, 성능 보장으로 읽히는 표현·원본 기능의 보존 여부·공식 사실과 제안의 혼동·근거 없는 버전 단정·확인하지 않은 검증 주장을 점검한다.
