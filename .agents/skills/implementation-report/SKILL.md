# 핵심 구현 코드 보고서

실제 구현한 코드와 해결한 문제를 파일명별 코드 블록 중심의 간결한 보고서로 정리한다. 기본 산출물은 채팅에서 복사할 수 있는 Markdown이며, 사진은 사용자가 첨부할 수 있도록 촬영 대상을 글로 안내한다.

## 요청 유형 구분

- 사용자가 보고서 또는 개발 노트의 작성·갱신을 명시적으로 요청한 경우에만 아래 보고서 양식을 적용한다.
- '노션에 복붙 가능하게', '붙여 넣기 쉽게 정리'는 출력 형식 요청이다. 이 표현만으로 개발 가이드나 설명을 보고서·개발 노트로 바꾸지 않는다.

## 범위와 근거 확인

- 사용자가 파일·기능·날짜·커밋을 지정하면 그 범위를 우선한다. 대상 없이 호출하면 현재 대화에서 다룬 최근 구현을 중심으로 현재 파일과 Git 변경 기록을 확인한다. 오늘 작업 요청은 사용자의 시간대와 현재 날짜를 기준으로 조사한다.
- Git 작성일이나 수정일만으로 사용자의 오늘 구현이라고 단정하지 않는다. 대화와 diff를 함께 확인하고 팀원의 무관한 변경, 이전 작업, 아직 제안만 한 코드를 구분한다.
- 현재 코드를 보고한다. 직전에 주석이나 선언 배치를 정리했다면 정리가 끝난 파일을 다시 읽고 그 주석까지 포함해 발췌한다.
- Rider에 열린 코드가 대상이면 get_all_open_file_paths로 실제 열린 파일을 확인하고 IDE 내용과 저장된 파일의 차이를 고려한다. 단순 보고서 작성은 열린 파일만으로 범위를 강제하지 않으며 관련 구현도 읽을 수 있다.
- 제공 코드만으로 작성하라는 요청이면 그 자료를 기준으로 작성한다. 자료에서 확인되지 않은 구현이나 테스트 결과를 보태지 않는다.
- 참고 페이지가 제공되면 연결된 도구로 읽고 제목, 밀도, 문체, 코드·사진 배치를 참고한다. 읽기 도구에서 접근이 안 되면 지원되는 브라우저로 확인한다. 끝내 읽지 못하면 참고하지 못한 사실을 밝히고 사용자가 지정한 형식을 따른다.
- 기본 참고 예시는 애니메이션 블루프린트 보고서 https://app.notion.com/p/402f82d634ba80c5b850c90597e52163 이다. 사용자가 별도 참고를 주면 그 자료를 우선하며, 매번 이 페이지 조회를 필수로 만들지는 않는다.

## 기존 보고서의 누적 갱신

- 사용자가 보고서를 작성·갱신할 Notion 페이지 링크를 주면 해당 페이지의 기존 본문을 실제로 읽고 보고서의 기반으로 사용한다. 단순 형식 참고용이라고 지정한 페이지는 내용 통합 대상과 구분한다. 목적이 불명확하면 대화 맥락으로 판단하고 대상이 달라질 때만 확인한다.
- 페이지의 기존 구현 내용, 핵심 코드, 문제 해결 기록, 관련 링크를 현재 코드·대화·Git 변경과 대조하여 새 내용을 합친다. 기본 결과는 새 내용만의 추가분이 아니라 사용자가 한 페이지에 교체하여 붙일 수 있는 통합된 전체 본문이다. 추가분만 요청하면 그 요청을 따른다.
- 구현이 여러 날에 걸쳐 진행되었어도 하나의 기능 보고서 안에서 누적한다. 날짜나 기간 지정은 새로 조사할 작업 범위에 적용하며, 기존 페이지의 이전 기록을 자동으로 제외하는 조건으로 삼지 않는다.
- 기존 설명이 유효하면 유지하고, 같은 파일·함수·내용은 중복 없이 합친다. 현재 구현과 다른 과거 코드는 최종 코드로 갱신한다. 이전 방식은 해결 원인 설명에 필요한 경우에만 과거 구현임을 밝혀 남긴다.
- 기존 본문과 현재 자료가 충돌하면 현재 파일, 브랜치와 변경 기록을 확인한다. 자료만으로 최신 여부를 확정할 수 없으면 임의로 기존 사실을 삭제하거나 새 제안을 구현 완료로 바꾸지 않고 불확실한 항목을 별도로 표시한다.
- 기존에 첨부된 사진·영상·캡션의 위치와 역할을 확인한다. 채팅에 미디어를 그대로 전달하기 어렵다면 본문에 `기존 사진 유지: ...`로 해당 위치를 명시하고, 새 자료가 필요한 위치에는 `첨부 권장 사진: ...`을 작성한다. 기존 사진을 새로 촬영해야 하는 것처럼 안내하거나 만료되는 미디어 URL을 영구 링크로 사용하지 않는다.
- 페이지가 잘리거나 접근되지 않으면 기존 본문을 읽지 못한 사실과 범위를 알린다. 확인 가능한 신규 구현 초안은 작성할 수 있지만, 기존 내용까지 보존한 누적 갱신본이라고 주장하지 않는다. 누적본 완성에 필요한 기존 본문 제공 또는 접근 가능한 링크를 요청한다.
- 링크 제공은 페이지 읽기와 통합본 작성 요청이며 게시 권한을 뜻하지 않는다. 기본 결과는 채팅에 제공한다. 실제 갱신을 명시적으로 요청받은 경우에만 쓰기 직전에 페이지를 다시 읽어 동시 편집을 확인하고, 관련 도구 지침에 따라 기존 미디어·속성과 무관한 내용을 보존하여 수정한다.

## 보고서 형식

- 각 보고서 본문의 맨 위에는 아래 문구와 개발 노트 링크 자리를 항상 넣는다. 여러 보고서를 작성하면 각 보고서마다 반복하고, 제목과 구현 설명은 그 아래에 배치한다.

  ```markdown
  핵심 코드와 개발 노트 링크를 첨부하였다.

  \> 개발 노트 링크
  ```

- 상단의 개발 노트 URL은 사용자가 직접 첨부한다. `> 개발 노트 링크`는 링크를 걸 수 있는 일반 텍스트로 제공하고, 예시 URL이나 참고용으로 받은 URL을 자동 삽입하지 않는다.
- 상단 고정 문구 외에는 개발 노트 언급을 최소화한다. 개발 노트는 작성 근거로 활용하되, 본문은 보고서만 읽어도 구현 목적·핵심 흐름·결과를 이해할 수 있도록 작성한다. 단순히 참고했다는 이유로 '개발 노트에 따르면', '개발 노트에 기록하였다' 같은 표현을 반복하지 않는다.
- 상세 실험 과정이나 추가 자료 등 개발 노트를 직접 참고하는 것이 독자에게 꼭 도움이 될 때만 본문에서 언급하거나 관련 링크를 안내한다. 핵심 설명을 외부 문서로 대신하지 않는다.
- 독립적으로 이해할 수 있게 작성하되 기존의 간결한 파일명·핵심 코드·짧은 설명 수준을 유지한다. 배경 이론, 전체 코드, 어려운 용어를 과도하게 늘리지 않는다. 근거의 불확실성이나 테스트 확인 범위는 필요한 만큼 짧게 구분한다.
- 바로 붙여 넣을 수 있도록 본문은 '~이다', '~하였다', '~하도록 구성하였다' 형태로 작성한다. 대화형 서문이나 제안형 튜토리얼로 시작하지 않는다.
- 보고서의 제목 단계는 대제목 `##`, 중제목 `###`, 소제목 또는 파일 이름 `####`로 통일한다. 보고서·기능 제목은 `##`, 구현 항목은 `###`, 그 아래 세부 항목·파일명·에셋명은 `####`로 작성하며, 본문에 `#` 제목은 사용하지 않는다.
- 제목 단계 참고는 [261111 개발노트](https://app.notion.com/p/261111-415f82d634ba80d2ad0bf470e89183e2)이다. 이 자료는 개발 노트이므로 제목 계층만 참고하고, 상세 작업 과정이나 문서 전체 구성을 핵심 구현 코드 보고서의 필수 형식으로 가져오지 않는다. 형식 적용만을 위해 매번 조회할 필요는 없다.
- 제목과 구현 결과를 짧게 제시하고, 핵심 코드는 `#### TBPlayer.cpp`처럼 실제 확장자를 포함한 파일명 제목 아래 언어를 지정한 코드 블록으로 제공한다.
- 보고서·개발 노트의 파일 안내는 `TBCharacterBase.h`처럼 확장자를 포함한 파일명만 쓴다. 제목·본문·표의 파일 안내에 절대 경로, 상대 디렉터리 경로, 파일 링크나 Markdown 링크를 넣지 않는다. 컴파일에 필요한 코드 내부의 `#include` 경로와 외부 근거 링크는 유지한다.
- 원본 코드를 정확히 발췌한다. 식별자·조건·수치·주석을 보고서용으로 임의 변경하지 않는다. 변경하지 않은 부분은 아래 발췌 규칙에 따라 `...`으로 생략할 수 있다. 생략 표시의 의미는 필요하면 문서 처음에 한 번만 설명하고 코드마다 발췌 안내를 반복하지 않는다.
- 독자가 변경 의도를 이해할 만큼의 선언과 함수만 담는다. 이미 제시했거나 변경하지 않은 코드, 무관한 입력 처리, 긴 전체 파일을 반복하지 않되, 새 구현에 필요한 헤더 선언과 include를 간결함을 이유로 누락하지 않는다. 설명에 필요하면 같은 파일을 기능별로 나눠 발췌할 수 있다.
- 각 구현은 목적과 결과를 짧게 설명한다. 문제 해결 부분은 증상, 확인한 원인, 최종 수정의 관계를 기술하며 폐기한 코드는 기본적으로 싣지 않는다.
- ABP 전이 조건 등 에디터 설정은 C++ 소스인 것처럼 제시하지 않고 상태명별 text 블록 또는 표로 정리한다. 대화에서 확인한 설정인지 실제 에셋에서 확인한 설정인지 근거 범위를 유지한다.
- 관련 위치에 `첨부 권장 사진: ...`을 넣는다. 상태 머신 전체, 전이 규칙의 조건, 입력 동작 비교 등 검증에 필요한 화면과 촬영 포인트를 구체적으로 적는다. 직접 사진을 생성·캡처·첨부하는 것은 별도 요청이 있을 때만 수행한다.
- 모르는 링크, 완료율, 담당자, 성능 수치, 빌드·멀티플레이 테스트 통과 여부는 만들어 내지 않는다.

## 코드 맥락과 발췌

- 보고서·개발 노트는 구현 의도와 동작을 자연스럽게 설명한다. `작성 대상`, `추가 파일`, `대상 함수`, `추가 위치`, `교체 위치` 같은 고정 항목이나 생성·삽입 절차를 코드마다 붙이지 않는다.
- 파일명 제목 아래에서 함수 선언부나 관련 기존 코드 한두 줄을 함께 보여 주고, 그 흐름에 새 코드를 이어 배치한다. 코드만 봐도 어느 함수에서 어떤 처리 다음에 실행되는지 알 수 있도록 필요한 맥락을 남긴다.
- 위치가 헷갈리는 경우에만 '충돌한 액터를 얻은 뒤 대상의 Cue를 선택한다'처럼 설명 문장에 자연스럽게 녹인다. 코드에서 이미 드러나는 파일·함수·위치 정보를 별도 항목으로 반복하지 않는다. 멤버 선언도 필요한 경우 접근 지정자나 주변 멤버로 맥락을 보여 준다.
- 긴 함수에서 기존과 동일한 부분은 `...`으로 생략하고 핵심 코드와 위치를 식별할 앞뒤 코드만 남긴다. 함수 선언부·중괄호와 필요한 분기·스코프를 유지하고, 새로 추가·수정하는 로직을 생략 표시 안에 숨기지 않는다. 짧은 함수는 전체 코드를 제공해도 된다.
- 새 멤버·Getter·함수 인자 등 이해에 필요한 연결은 관련 코드와 짧은 설명으로 함께 보여 준다. 보고서를 세세한 파일 생성·편집 절차 목록으로 늘리지 않으며, `...`이 있는 발췌를 완성된 함수 전체 교체 코드라고 안내하지 않는다.

## 헤더와 구현의 연결

- C++ 클래스를 다룰 때는 `.h`와 `.cpp`를 함께 확인한다. 새 클래스는 헤더 전체를 함께 제공하고, 기존 클래스는 새로 추가하거나 수정한 선언을 접근 지정자와 필요한 주변 코드로 보여 준다.
- 헤더에는 구현에 대응하는 생성자·함수 선언, 멤버 변수, 기본값, 접근 지정자를 빠짐없이 담는다. Unreal 클래스는 필요한 상속 관계, 모듈 API 매크로, `UCLASS`, `GENERATED_BODY`, `UPROPERTY` 지정자와 메타데이터도 포함한다. 새 선언에는 역할을 설명하는 주석을 붙인다.
- 설정값 표나 설명은 선언 코드를 보충하는 용도이다. `.cpp`에서 사용하는 새 멤버나 함수의 헤더 선언을 표 또는 설명만으로 대신하지 않으며, 필요한 선언을 `...` 안에 숨기지 않는다.
- 새 구현에 필요한 include와 전방 선언을 해당 파일의 코드로 함께 제공한다. 새 Unreal 헤더에서는 `.generated.h`를 마지막 include로 두고, `.cpp`에서 완전한 타입이 필요한 경우 해당 헤더를 포함한다. 이미 제시한 선언이나 include는 불필요하게 반복하지 않는다.

## 작업 경계

- 이 스킬의 양식은 명시적으로 요청한 보고서·개발 노트 작성용이다. 소스 주석 추가, 변수·함수 위치 변경, 기능 수정, 커밋·push는 별도 지시 없이는 수행하지 않는다.
- Notion 문서를 참고하는 것은 읽기만 허용한다. 기본 결과는 채팅으로 제공하며, Notion 페이지를 생성·수정하지 않는다. 사용자가 게시까지 명시적으로 요청하면 대상과 범위를 확인하여 해당 도구로 처리한다.
- 보고서를 파일로 저장하는 것은 요청받았을 때 수행한다. 채팅 보고서를 위해 불필요한 문서 파일을 저장소에 만들지 않는다.

## 전달 전 확인

- 요청이 보고서·개발 노트인지 개발 가이드인지 구분하였으며, 노션 복사 형식만을 이유로 보고서 양식을 적용하지 않았는지 확인한다.
- 파일 안내가 링크·경로 없는 파일명인지 확인한다.
- 각 보고서 맨 위에 고정 문구와 사용자가 링크를 첨부할 텍스트가 있는지 확인한다.
- 대제목은 `##`, 중제목은 `###`, 소제목·파일명·에셋명은 `####`인지 확인한다.
- 본문이 개발 노트를 읽지 않아도 이해되며, 불필요한 개발 노트 언급이나 과도한 상세 설명이 없는지 확인한다.
- 누적 갱신 시 기존 페이지의 유효한 내용과 링크·사진 위치가 보존되고 신규 내용이 중복 없이 반영되었는지 확인한다.
- 파일명, 클래스명, 발췌 코드가 현재 원본과 일치하는지 확인한다.
- `.cpp`에서 사용하는 새 멤버·함수의 헤더 선언과 필요한 include·전방 선언이 제공되었는지 확인한다. 선언과 정의의 인자·반환형·const 및 재정의 지정이 맞고, 설정값 표가 선언 코드를 대신하지 않았는지 확인한다.
- 함수 선언부와 주변 코드에서 실행 맥락을 파악할 수 있는지, 헷갈리는 위치만 자연스러운 설명으로 보완했는지 확인한다. 고정된 작성 대상·추가 위치 안내나 반복적인 발췌 문구가 없고, `...`은 변경하지 않은 부분에만 사용되었는지 확인한다.
- 이번 작업과 무관한 이전 코드가 핵심 변경으로 표시되지 않았는지 확인한다.
- 실제 구현, 에디터 설정, 향후 계획, 사용자 확인 결과와 에이전트의 검증을 구분한다.
- 사진 안내는 글로만 남기고, 사용자가 한 번에 복사할 수 있는 완성된 본문을 제공한다.
